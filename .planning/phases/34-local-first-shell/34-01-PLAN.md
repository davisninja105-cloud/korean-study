<objective>
Ship the local-first cache end-to-end on one route. `GET /api/version` starts carrying a
build ID, `lib/local-cache.ts` becomes the client's IndexedDB route cache keyed by that
build ID, and `/habits` reads it on mount so a repeat visit paints real streak and
heatmap data before the network answers — including with the network fully off.

Purpose: this is the thin vertical slice that proves the whole architecture (server build
ID → build-ID-namespaced database → cache-first mount read → version-checked background
revalidation → manual escape hatch) before it is expanded across Study, Cards, and Home.
If the slice is wrong, it is wrong after one commit, not ten.

Output: `lib/local-cache.ts` (new), a `buildId` field on `GET /api/version`, a
cache-first `/habits` with its own `handleRefresh` pull-to-refresh, unit coverage under
`fake-indexeddb`, and a Playwright spec proving first paint from cache and offline
render.
</objective>

<assumption_delta_decision>
**Transition detected:** singular → plural on "source of truth for a route's DTO
payload". Before this phase there is exactly one producer (the RSC page's Prisma read,
delivered as `initial*` props, with `FreshnessWatcher`'s JSON backstop as a redundant
second delivery of the *same* server value). After this phase there are two genuinely
independent producers: server-fresh (RSC props / API fetch) and cache-fresh (IndexedDB).

**Decision: promote the generalised identity — do not add-alongside.** "Current known
state for a route" is modelled once, in `lib/local-cache.ts`, as a `CacheEntry<T>` that
carries the `dataVersion` it was built from. Each `*Client.tsx` resolves a single
override value from that entry; RSC props become the *cold-start fallback source* for
that same identity, not a parallel competing one.

**Rationale:** adding a second parallel path alongside the existing prop/backstop dance
is exactly the failure mode D-00 rule 3 forbids ("replace layers, don't add one") and
RESEARCH.md's anti-pattern section names by title. Promoting the identity is what makes
`FreshnessWatcher`'s JSON backstop provably redundant in plan 34-05, rather than merely
duplicated.

**Advisory only** — this does not block the phase.
</assumption_delta_decision>

| T-34-02 | Information Disclosure | IndexedDB (unencrypted client storage) | low | accept | Cached content is exactly what the authenticated UI already displays (streak days, mastered count, FSRS state counts). | T-34-03 | Denial of Service (self-inflicted) | stale DTO shape after a deploy | medium | mitigate | The database is named `ks-cache-<buildId>`; a new build opens a new, empty database, so an old-shape entry can never be handed to a newer component.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network → service-worker CacheStorage | Any HTTP response the worker receives can become the cached document served as an app route while offline. A redirect crossing this boundary is untrusted content arriving under a trusted key. |
| server HTTP status → client durable queue policy | A single integer from the server decides whether a durably-stored, not-yet-applied review is retained or destroyed. Misclassification in either direction is data loss or an unbounded retry. |
| UI undo gesture → durable queue mutation | A user gesture deletes a durable IndexedDB record selected by an idempotency key. The selector is the whole authorization. |
| service-worker source → generated public/sw.js | The worker actually executed is generated by scripts/gen-sw.mjs; a hand-edit to the artifact silently diverges from reviewed source on the next build. |

<flagged_assumptions>
Surfaced rather than silently resolved — this phase has no SPEC.md, so the edge-coverage predicates above were authored by the planner, not read from a contract.

1. **Residual undo-versus-flush race (OFFLINE-03 concurrency, partially resolved).** If a flush has already issued the POST for a queued entry at the instant undo fires, `removeQueuedReviewByKey` deletes a row whose request is already in flight. The grade can then land server-side after the undo POST reverted it. This plan does NOT add a mutex or a cross-tab lock for that window; it relies on the pre-existing `ReviewLog.idempotencyKey` UNIQUE constraint plus the fact that undo is a user gesture that follows the grade by seconds while the flush window is milliseconds wide. Encoded as a `verification: backstop` truth rather than an `explicit` one. If the developer wants this closed rather than bounded, it needs its own phase (it overlaps WR-02's cross-tab flush coordination, which 35-VERIFICATION.md scoped out).
2. **Trailing-slash strictness (OFFLINE-01 adjacency).** The predicate treats `/study/` and `/study` as different keys and caches neither under the other. This is fail-closed and correct for this app (Next.js `trailingSlash` defaults to false, so the requested key and the served pathname agree), but it is a planner-chosen interpretation, not a documented product rule. Consequence of being wrong: a route silently stops being cached, degrading offline coverage — never serving wrong content.
3. **Undo while offline cancels the queued entry even though the undo POST cannot succeed.** 35-REVIEW.md's CR-03 fix text says "call it from handleUndo's success path (and ideally also its abort path)". This plan makes the cancel-path call mandatory rather than optional, because the success path alone leaves the offline-undo case — the single most likely real occurrence — unfixed. The tradeoff: if the undo POST later fails permanently, the grade is neither applied nor undone server-side, which matches the user's intent but leaves client state unrestored (a pre-existing wart in `handleUndo`'s failure branch, not introduced here).
</flagged_assumptions>

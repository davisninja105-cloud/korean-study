<objective>
Make a review graded in airplane mode durable: write it to IndexedDB the moment the background save gives up, survive a force-quit, and replay it exactly once when the device comes back online or the app returns to the foreground — with no Background Sync API anywhere, because it never fires on iOS.

The server needs no changes at all. `app/api/review/route.ts` is already idempotent: a duplicate idempotency key hits the `ReviewLog` unique constraint and is treated as a successful no-op. This plan reuses that discipline rather than inventing a second one.

  <name>Task 1: The durable queue — its own database, sequential flush, unit-proven</name>
  <reversibility rating="one-way">Storing the queue inside the build-id-namespaced route-cache database would mean a deploy landing during an offline session orphans already-graded reviews in a database the app will never reopen; data lost that way cannot be recovered afterwards. Recorded per D-00, which the developer already locked — no gate needed, only the record.</reversibility>
  <files>lib/offline-queue.ts, tests/offline-queue.test.ts</files>
  <action>
Create `lib/offline-queue.ts` as a plain module with no `use client` directive, importing only from `idb` — the same shape and conventions as `lib/local-cache.ts`, including its silent-fallback discipline where every storage operation is wrapped so a failure degrades to a no-op and never propagates into a client render.

Export a constant `QUEUE_DB_NAME` holding `ks-offline-queue` and a constant `QUEUE_STORE` holding `reviews`. The database name is deliberately a fixed literal with no build id in it, and this module must not import the route cache's prefix constant. This is D-00, carried into the phase as a locked non-negotiable constraint: the route cache is opened fresh on every new build id and an old build's database is simply never reopened, which is exactly the event a review queue has to survive — a deploy landing while a device is offline with unflushed grades. Put that reasoning in a leading comment block, in the same style `lib/local-cache.ts` uses to document why its own rules exist.

Export an interface `QueuedReview` with an optional numeric `id`, a `cardId` string, a numeric `rating`, an `idempotencyKey` string, and a `queuedAt` ISO string used only for debugging. Open the store lazily inside a memoized `getDb` helper — never at module scope, never as an import-time side effect — with an auto-incrementing key path on `id`, so cursor iteration order is enqueue order by construction rather than by sorting a stored timestamp.

Export `enqueueReview(entry)` taking the record without its key and adding it to the store. Export `readQueue()` resolving the full list in key order, returning an empty array on any storage failure. Export `flushQueue(post)` where `post` is an injectable async function that takes a queued entry and resolves to an object carrying a numeric `status`; default it to a real request against the review endpoint sending exactly `cardId`, `rating`, and `idempotencyKey` as JSON. Injecting the transport is what lets the unit tests drive every branch without stubbing the global fetch.

`flushQueue` resolves an outcome object with numeric `flushed`, `dropped`, and `remaining` counts, and behaves as follows. Hold a module-level boolean reentrancy flag; if a flush is already in flight, return immediately with all counts at zero so two triggers firing together cannot interleave, and clear the flag in a finally block. Read the whole queue once, then walk it one entry at a time with an await between each — strictly sequential, never a concurrent batch. The server reads current card state fresh on every request rather than validating a client-supplied prior state, so two grades of the same card replayed out of order would each succeed individually while producing a different final scheduling state than the learner actually experienced; sequential enqueue-order replay is what prevents that. For a 2xx response, delete the entry and count it flushed. For a 4xx response, delete the entry and count it dropped — the card was deleted or the payload is no longer valid, and retrying forever would never help. For a 5xx response or a thrown network error, stop the walk immediately, leaving that entry and every later entry in the store for the next trigger; do not delete and do not continue to the next entry, because continuing would break enqueue ordering for a card graded more than once.

Never mint a new idempotency key on flush. The key is generated once at grade time and stored with the entry; the server's unique constraint on that key is what makes a re-flush after a mid-flush force-quit a safe no-op rather than a double-applied grade.

Create `tests/offline-queue.test.ts` mirroring `tests/local-cache.test.ts`'s setup, with the `fake-indexeddb/auto` polyfill imported as the very first line before the module under test. Cover: an enqueued entry is readable back with its fields intact; multiple enqueues read back in enqueue order; a flush with an all-2xx transport empties the store and reports the right flushed count; a 4xx entry is deleted and counted dropped while later entries still flush; a 5xx entry stops the walk with that entry and all later ones still queued and the remaining count correct; a thrown transport error behaves identically to the 5xx case; the transport receives entries in enqueue order and is never called concurrently (record call start and end ordering in the stub); the transport receives the same idempotency key that was enqueued, and a second flush of an entry the transport reports as already-applied leaves the store empty rather than duplicating; and a flush invoked while another is in flight returns a zeroed outcome without touching the store.
  </action>

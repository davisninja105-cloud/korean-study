<objective>
Make "a study session runs on cached cards in airplane mode" literally true for a genuine cold launch, not just for a tab that was already open when the network dropped.

Two gaps stand between plan 35-01's service worker and OFFLINE-02. First, every one of Phase 34's cache-read effects short-circuits when `/api/version` is unreachable, because the `buildId` that names the IndexedDB database is only obtainable over the network — so offline, the cache that holds the cards is never opened. Second, the study pool is only ever cached as a side effect of visiting `/study`; per D-01 this phase adds proactive warming so offline readiness does not depend on that.

Purpose: OFFLINE-02.
Output: a `localStorage`-backed cache-context fallback in `lib/local-cache.ts` adopted at every call site, a Home-mount warm of the due session (D-01 through D-04), Vitest coverage, and a Playwright cold-offline study-session proof.
</objective>

  <name>Task 1: Last-known cache context — make the IndexedDB cache reachable with no network</name>
  <files>lib/local-cache.ts, components/HomeClient.tsx, components/StudyClient.tsx, components/CardsClient.tsx, components/HabitsClient.tsx, components/SettingsClient.tsx, tests/local-cache.test.ts</files>
  <action>
In `lib/local-cache.ts`, widen the exported `CacheContext` interface with a third, optional boolean field named `stale`. A context resolved live from the server omits it; a context recovered from storage sets it true. Every existing destructuring of `version` and `buildId` keeps compiling unchanged, so this is additive.

Export a module constant `LAST_CONTEXT_KEY` holding the storage key `ks-last-cache-context`, and an async function `fetchCacheContextOrLastKnown` returning the same nullable `CacheContext`. It calls the existing `fetchCacheContext` first; on success it writes the `{version, buildId}` pair to `localStorage` under that key inside a try/catch that swallows quota and private-mode failures, then returns the live context. On failure it reads the key back, parses it, and returns it only when the parsed value is a non-null object whose `version` and `buildId` are both strings — anything else, including an absent key, a parse error, or an environment with no `localStorage` at all, resolves to `null`. Guarding the shape matters: an unvalidated value would be used to name an IndexedDB database. Mark the recovered context with `stale: true`. Document the function with a leading comment block in the same style as the module's existing "Build-ID namespacing" and "Version-check revalidation" blocks, naming the offline cold-launch gap it closes and stating that `localStorage` is used rather than IndexedDB because the read must be synchronous-cheap and available before any database can be named.

Then replace every `fetchCacheContext()` call with `fetchCacheContextOrLastKnown()` at all eleven consuming call sites — three in `components/HabitsClient.tsx`, three in `components/StudyClient.tsx`, three in `components/CardsClient.tsx`, two in `components/HomeClient.tsx` — plus the one in `components/SettingsClient.tsx`. Update each file's import accordingly. Change nothing else about those effects: the existing early-return guard when the context is null stays, the cancellation guards stay, the revalidation conditions stay. The behavioural difference is only that the guard is now reachable-with-real-data offline instead of a dead end. Leave the write-stamping call site in `components/CardsClient.tsx` on the same wrapper — a device-originated card edit made offline belongs in the last-known build's database, which is exactly where the data it patches lives.

Extend `tests/local-cache.test.ts` with a describe block for the new function. Vitest runs in the node environment, so install a minimal Map-backed `localStorage` stand-in on `globalThis` in a `beforeEach` and a stubbed `globalThis.fetch`, restoring both afterwards. Cover: a live success returns the live context with no stale marker and writes the pair to storage; a subsequent failure returns the previously stored pair marked stale; a failure with nothing stored returns null; a stored value that is malformed JSON returns null; a stored object missing one of the two string fields returns null; a stored value whose fields are non-strings returns null; and a live success overwrites a previously stored older pair. Also assert the function does not throw when `localStorage` is entirely absent from the global scope.
  </action>

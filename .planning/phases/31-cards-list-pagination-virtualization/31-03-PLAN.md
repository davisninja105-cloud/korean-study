<objective>
Build the two backend pieces that CardsClient.tsx will need once sentences are dropped from the list
query: a full-card fetch endpoint for the Edit sheet (`GET /api/cards/[id]`), and D-07's independently
paginated Reading Practice endpoint (`GET /api/cards/sentences`, backed by a new `getSentencesPage()`).
Pure backend — this plan touches no client files, so it runs in parallel with 31-02 (both depend only
on 31-01, no file overlap).

Purpose: CARDS-01 requires sentences to be dropped from the list read; two consumers need them back on
demand — the Edit sheet (one card's sentences) and the Reading Practice tab (a full-deck paginated
stream of sentences). Both need a real server-side query; this plan builds both endpoints so 31-04 can
wire the client side against a complete backend contract.

Output: `GET /api/cards/[id]` (full `CardDTO`), `GET /api/cards/sentences` (new route, `SentencePageDTO`),
`getSentencesPage()` in `lib/cards-list.ts`, and test coverage for both.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-05 | Information Disclosure | `app/api/cards/[id]/route.ts` (GET) | low | accept | Single-tenant app, no per-user data; any authenticated session (gated by existing `middleware.ts` HMAC cookie) may already read any card via the existing `PUT`/`DELETE` handlers on the same route — this GET introduces no new exposure. |

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (document.cookie) → `app/layout.tsx` pre-paint script | The script trusts the cookie's *shape* only after a `try/catch`-wrapped `JSON.parse`; a malformed value must degrade silently, never throw and block render |
| Authenticated client → `PUT /api/settings` | Existing `middleware.ts` `ks_auth` gate already protects this route; unchanged by this plan |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-01 | Tampering | `app/api/settings/route.ts` (`ks_settings` cookie write) | low | mitigate | `httpOnly: false` is a deliberate, documented deviation for a cosmetic-only cookie; the PUT route continues to validate hex-color format server-side via the existing `HEX_RE`-backed `setButtonColor`/`setRewardColor`/`setReadingTextScale`/`setReadingAid` setters before the *validated* return values (not raw request body) are written into the cookie |
| T-30-02 | Information Disclosure | `ks_settings` cookie (non-httpOnly, readable via `document.cookie`) | low | accept | The cookie deliberately carries only non-secret UI preference data (hex colors, a float scale, a boolean) — never anything auth/session-related; a hypothetical future XSS reading this specific cookie learns nothing sensitive, unlike `ks_auth` which stays `httpOnly` and is unaffected by this plan |
| T-30-03 | Elevation of Privilege | `ks_settings` cookie mistakenly trusted as an authorization/identity signal by future code | medium | mitigate | `middleware.ts`'s `ks_auth`-based gate remains the sole access-control mechanism, untouched by this plan; enforced by the kept prohibition in this plan's `must_haves.prohibitions` — verify via `grep -rn "ks_settings" --include='*.ts' --include='*.tsx' app/ components/ middleware.ts lib/` and confirm every hit is inside `app/layout.tsx` or `app/api/settings/route.ts` |
| T-30-04 | Denial of Service (minor) | Pre-paint `<script>` cookie parse throwing and blocking first paint | low | mitigate | The entire parse-and-apply block is wrapped in a single outer `try{}catch(e){}` (matching the two existing pre-paint scripts in the same file) — any parse failure is a silent no-op, CSS `:root` defaults still apply |

</threat_model>
